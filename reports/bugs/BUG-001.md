# BUG-001: Store API — count в листингах равен размеру страницы, а не общему числу записей

| Поле | Значение |
|------|----------|
| ID | BUG-001 |

| Severity | Medium |
| Priority | P2 |
| Слой | API |

| Воспроизводимость | всегда |
| Статус | Confirmed (контур Б, детерминированный прогон) |

## Предусловия

Валидный publishable key (`.env: PUBLISHABLE_KEY`); доступ к цели через харнесс (--resolve).

## Шаги воспроизведения

1. `GET /store/products?limit=1` с заголовком `x-publishable-api-key`.
2. `GET /store/products?limit=2`.
3. `GET /store/products?limit=10`.

## Ожидаемый результат

`count` одинаков во всех трёх ответах и равен общему числу записей, доступных ключу (4 —
сверено с `GET /admin/products`, где count=4 при любом limit). Основание: контракт листингов
Medusa v2 (docs.medusajs.com/api/store) — `count` = общее число записей; поведение Admin API
в этой же системе.

## Фактический результат

`count` равен размеру запрошенной страницы: limit=1 → count=1; limit=2 → count=2; limit=10 → count=4.
Пагинация на стороне витрины, опирающаяся на count, занижает число страниц.

## Артефакты

- `reports/artifacts/count-limit-1.json`, `count-limit-2.json`, `count-limit-10.json`
- сводка прогона: `reports/artifacts/verify-candidates-*.json` (проверка «count: стабильность между limit» = FAIL)
- воспроизведение: `npx tsx scripts/ts/verify-candidates.ts`

## Примечания

- Admin API в той же системе считает корректно (count=4 при limit=1) — рассогласование Store ↔ Admin.
- Не путать с видимым скоупом: Store-ключ отдаёт 4 из 5 товаров каталога (см. registry/assumptions.md A-003).
