## Предусловия

Валидный publishable key.

## Шаги воспроизведения

1. `GET /store/shipping-options?cart_id=cart%00qa` → **HTTP 500**
2. `GET /store/shipping-options?cart_id=T%F0%90%86%83%00%C2%AF%17%F3%91%84%8A%C2%BB%C2%91` (NUL + не-UTF-юникод, из фаззинга) → **HTTP 500**
3. Контраст: `GET /store/products?q=abc%00def` → **HTTP 500** (NUL ломает и строковый поисковый параметр)
4. Контроль (та же сессия): валидный `cart_id` → 200; несуществующий текстовый → 404;
   не-UTF-юникод **без** NUL → 404; `GET /store/carts/cart%00qa` (path, не query) → 400.

## Ожидаемый результат

Параметр с недопустимым символом отклоняется валидационной ошибкой (400), как это делают
другие маршруты (cart GET по path даёт 400). Основание: контракт обработки ошибок v2;
внутренняя согласованность.

## Фактический результат

500 `{"code":"unknown_error","type":"unknown_error","message":"An unknown error occurred."}`
при любом NUL (`%00`) в query-параметре. Юникод сам по себе обрабатывается корректно (404) —
причина именно в NUL-байте.

## Примечания

- Read-only: корзины и данные не затрагиваются (проверено: запросы только GET).
- Уживает BUG-005 в одну картину: сервер системно превращает класс невалидных входов
  (отрицательная пагинация, NUL в query) в необработанные 500 вместо структурированных 400.
- Секьюрити-аспект: NUL-инъекция классически используется для обхода фильтров; здесь она
  не даёт доступа к данным (500, а не исполнение), но показывает отсутствие нормализации
  входа до слоя БД.
